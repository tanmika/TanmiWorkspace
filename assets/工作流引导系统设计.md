# 工作流引导系统设计

> 调研日期：2026-01-05
> 状态：设计中

## 背景

当前 TanmiWorkspace 的工作流存在两个核心问题：

1. **信息阶段仅限初始化**：信息收集/总结只能在工作区创建时使用，执行中无法触发
2. **执行阶段缺乏引导**：AI 不知道何时推进节点、如何填写需求、何时使用特殊状态

## 目标

- 让信息收集/总结成为通用能力，可在任意节点、任意时刻启动
- 为执行阶段提供结构化引导，明确状态转换条件和记录规范
- 保持信息阶段和执行阶段的清晰边界

## 一、调研发现

### 1.1 Superpowers 框架

**项目位置**：`/Users/tanmika/ThirdPart/superpowers`

#### 核心架构：三层递进 + 双阶段审查

```
设计层 (Brainstorming)
    ↓ 需求规范
计划层 (Writing Plans)
    ↓ 原子任务（2-5分钟/步，完整代码）
执行层 (Executing Plans / Subagent-Driven)
    ↓ 每任务两阶段审查
    ├─ Spec Compliance Review（做了什么？）
    └─ Code Quality Review（做得好吗？）
```

#### 关键设计理念

| 设计 | 说明 |
|------|------|
| **强制流程** | 不是建议，是"Iron Law"——违反就删除重来 |
| **原子任务** | 每步 2-5 分钟，完整代码而非伪代码 |
| **双阶段审查** | 分离"是否正确"和"是否优质" |
| **信息隔离** | 子代理不读文件，控制者粘贴需要的内容 |
| **理由对抗** | 明确列举并反驳 AI 常见借口 |
| **阻塞即停** | 遇到问题立即停止，不要猜测 |

#### 执行阶段的 SOP（executing-plans skill）

```markdown
Step 1: Load and Review Plan
- 读取计划
- 评估是否有问题
- 有问题 → 先提，不要开始

Step 2: Execute Batch（默认 3 个任务）
- 标记 in_progress
- 按步骤执行
- 运行验证
- 标记 completed

Step 3: Report
- 展示实现内容
- 展示验证结果
- 说："Ready for feedback."

Step 4: Continue
- 根据反馈调整
- 执行下一批
```

#### 阻塞规则

```
STOP immediately when:
- Hit a blocker mid-batch
- Plan has critical gaps
- You don't understand an instruction
- Verification fails repeatedly

Ask for clarification rather than guessing.
```

- `/skills/writing-plans/SKILL.md` - 计划生成
- `/skills/executing-plans/SKILL.md` - 批处理执行

### 1.2 行业最佳实践

#### 任务分解原则

> 每个子任务应该是：**Specific**（明确）、**Achievable**（可实现）、**Ordered**（有序）

来源：[Breaking Down Tasks for AI Agents](https://mbrenndoerfer.com/writing/breaking-down-tasks-task-decomposition-ai-agents)

#### 任务粒度

> 像写人类开发者任务一样，2-3 story points 最佳，5 points 是上限，8 points 就太大了

来源：[AI Coding Task Management](https://story.haxitag.ai/2025/04/ai-coding-task-management-best.html)

#### 状态持久化（LCMP）

```
./context/
├─ state.md      # 当前状态、活跃任务、下一步
├─ schema.md     # 数据结构、文件位置
├─ decisions.md  # 技术决策及理由、放弃的路径
└─ insights.md   # 累积发现、模式观察
```

来源：[How I Solved the Biggest Problem with AI Coding Assistants](https://medium.com/@timbiondollo/how-i-solved-the-biggest-problem-with-ai-coding-assistants-and-you-can-too-aa5e5af80952)

#### 工作流模式

> **Plan → Act → Review → Repeat**，分离规划和执行会话

来源：[Minimalist Claude Code Task Management](https://medium.com/nick-tune-tech-strategy-blog/minimalist-claude-code-task-management-workflow-7b7bdcbc4cc1)

经过核查，原始问题需要修正：

| 原始假设 | 实际情况 | 真正问题 |
|---------|---------|---------|
| "执行阶段缺乏引导" | 已有 executing-task skill | **AI 不知道要调用它** |
| "信息阶段仅限初始化" | capability_select 已支持 nodeId | **缺少引导让 AI 主动使用** |
| "状态使用不当" | 状态机完整 | **blocked 状态缺失 + 引导不足** |

**核心问题**：现有机制是完备的，但 **AI 不知道何时、如何使用它们**。

## 三、设计方案（修订版）

基于核查结果，问题不是"缺少机制"，而是"AI 不知道使用机制"。修订后的方案聚焦于**引导优化**而非新增功能。

### 3.1 执行阶段：让 AI 知道何时调用 Skill

#### 问题

- executing-task skill 存在，但 AI 不知道要调用它
- GuidanceService 有引导，但未强制要求调用 Skill

#### 方案：增强 Guidance 的 actionRequired

在执行节点 `start` 时，返回 `actionRequired: invoke_skill`：

```typescript
// 执行节点 start 时
if (nodeType === "execution" && action === "start") {
  return {
    actionRequired: {
      type: "invoke_skill",
      skill: "executing-task",
      message: "⚠️ MUST 调用 Skill(executing-task) 获取执行 SOP"
    }
  }
}
```

#### 方案 B：在 GuidanceContent 中强化

更新 `execution_start` 场景的 L0 引导：

```typescript
// 现有
"开始执行任务，请按计划实施并用 log_append 记录进度"

// 改为
"⚠️ MUST 调用 Skill(executing-task) 获取执行 SOP，NEVER 直接开始实施"
```

### 3.2 信息阶段：让 AI 知道可以随时启动

#### 问题

- capability_select 已支持 nodeId，但 AI 不知道可以在执行中使用
- starting-info-flow skill 存在，但未被主动调用

#### 方案：在阻塞场景引导使用

更新 `execution_blocked` 或新增 `execution_need_research` 场景：

```typescript
execution_need_research: {
  L0: "需要调研？调用 Skill(starting-info-flow) 启动信息收集流程",
  L1: `
    遇到未知技术或需要调研时：
    1. 调用 Skill(starting-info-flow)
    2. 选择合适的能力（tech_research/diagnosis/context_discovery）
    3. 在当前节点下创建信息收集子节点
    4. 完成后继续执行
  `
}
```

#### 触发条件

| 条件 | 引导 |
|------|------|
| 执行节点 fail + reason 包含 "不了解"/"需要调研" | 引导使用 starting-info-flow |
| 用户明确请求调研 | 引导使用 starting-info-flow |
| 执行节点阻塞时间过长 | 引导考虑信息收集 |

### 3.3 状态使用：增加 blocked 状态（可选）

#### 现状

当前只有 `failed` + `retry`，语义上是"失败后重试"。

#### 问题

"阻塞"和"失败"语义不同：
- **blocked**：外部依赖阻塞，等待解除后继续
- **failed**：方向错误或不可行，需要重新规划

#### 方案 A：不改状态机，用 reason 区分

```typescript
// 阻塞
node_transition(action="fail", reason="[BLOCKED] 等待 API 密钥配置")

// 真正失败
node_transition(action="fail", reason="[FAILED] 方案不可行，需重新设计")
```

#### 方案 B：新增 blocked 状态

```typescript
EXECUTION_TRANSITION_TABLE: {
  pending:      { start: "implementing" }
  implementing: { submit: "validating", complete: "completed", fail: "failed", block: "blocked" }
  validating:   { complete: "completed", fail: "failed" }
  blocked:      { unblock: "implementing", fail: "failed" }  // 新增
  failed:       { retry: "implementing" }
  completed:    { reopen: "implementing" }
}
```

### 3.4 强制规则：增加 Iron Law

借鉴 Superpowers，在 executing-task skill 中增加强制规则：

```markdown
## Iron Law（不可违反）

### 不理解就问
- NEVER 猜测需求含义
- NEVER 假设缺失的信息
- 有疑问 → 先问用户或调用 starting-info-flow

### 阻塞就停
- 遇到无法解决的阻塞 → 立即 fail + reason
- NEVER 跳过阻塞步骤继续执行
- NEVER 用 workaround 绕过核心问题

### 错了就放弃
- 发现方向错误 → 立即 fail
- NEVER 硬撑完成错误的任务
- NEVER 等到最后才报告问题

### 过程要记录
- 每个关键步骤 → log_append
- 遇到问题 → problem_update
- NEVER 只有最终结果
```

### 3.5 理由对抗：反驳常见借口

参考 Superpowers 的设计，在 skill 中增加常见借口的反驳：

```markdown
## 常见借口与反驳

| 借口 | 反驳 |
|------|------|
| "需求不够清晰，但我可以猜" | 猜错的成本远高于问一句的成本 |
| "这个阻塞可以绕过" | 绕过 = 技术债务，先确认是否允许 |
| "快完成了，先不记录" | 记录是给未来的自己和用户看的 |
| "这个问题不重要" | 用户决定重要性，你只负责报告 |
| "测试通过就行" | 测试通过 ≠ 需求满足，需对照 acceptanceCriteria |
```
