# TanmiWorkspace 用户手册

> AI 编程任务的结构化管理方案

---

## 这是什么？

TanmiWorkspace 就像是 AI 的项目管理系统。

想象你在和一个能干但健忘的同事合作——他很聪明，但对话一长就忘了早期的决策；任务一复杂就容易跑偏。TanmiWorkspace 就是给这个"同事"配的任务管理工具：把大任务拆成小步骤，每步都记录下来，随时能回顾进度。

### 核心概念

| 概念 | 说明 |
|------|------|
| **工作台** | TanmiWorkspace 本身，管理所有工作区的平台 |
| **工作区** | 单个任务的完整记录，包含一棵任务树 |
| **节点** | 任务树中的每个任务单元 |

工作台是你的办公桌，工作区是桌上的每个项目文件夹，节点是文件夹里的待办事项。

> 更多概念（节点类型、状态、派发模式等）请参阅 [术语表](#术语表)。

### 解决什么问题？

| 问题 | 没有工作台时 | 有工作台后 |
|------|-------------|-----------|
| **AI 忘事** | 对话超过 10 轮，AI 忘了开头说的需求 | 所有决策都记录在节点里，随时查阅 |
| **过程黑盒** | 不知道 AI 做了什么、为什么这样做 | WebUI 实时展示任务树和执行日志 |
| **粒度失控** | AI 一次规划太多，执行质量下降 | 强制拆分，一次只做一个任务 |
| **难以继续** | 关掉对话就没了，下次从头来 | 工作区持久化，随时恢复进度 |

### 谁会受益？

- **你**：知道 AI 在做什么、做到哪了，能随时调整方向
- **AI**：有结构化的任务管理，不再迷失在长对话中
- **项目**：所有变更有迹可循，出问题能回溯

## 快速开始

### 安装

```bash
npm install -g tanmi-workspace
tanmi-workspace setup  # 自动检测环境并配置
```

**启动 WebUI 服务**（推荐）：

```bash
tanmi-workspace webui  # 启动后保持终端窗口打开
```

> **为什么要手动启动？** AI 助手启动时会自动启动 WebUI，后续打开的新对话会跳过启动共用服务，但关闭该对话窗口后 WebUI 也会停止，导致 WebUI 不可用。手动启动可以让 WebUI 独立运行，不受对话窗口影响。

启动后访问终端显示的地址（默认 `http://localhost:19540`）即可查看任务进度。

**其他管理命令**：
```bash
tanmi-workspace webui status  # 查看服务状态
tanmi-workspace webui stop    # 停止服务
tanmi-workspace webui restart # 重启服务
```

端口被占用时可指定其他端口：`HTTP_PORT=19550 tanmi-workspace webui`

**支持的 AI 助手**：

| AI 助手 | 支持程度 | 说明 |
|---------|---------|------|
| **Claude Code** | 完全支持 | 所有功能可用，推荐使用 |
| **Cursor** | 基础支持 | subagent 和 skill 支持有限（见下方说明） |
| **其他 MCP 兼容助手** | 基础功能 | 支持 MCP 即可使用核心功能 |

Cursor 的限制：派发模式会降级为主进程执行（流程依然完整，但无法真正并行）；Skill 转化为读取说明形式，上下文消耗略有增加。

其他智能体：只要支持 MCP 协议即可使用基础功能。如果智能体额外支持 subagent、skill 等特性，对应功能即可使用。配置方式需自行操作，可运行 `tanmi-workspace -h` 查看帮助。

### 第一次使用

**触发工作台的方式**：在对话中明确提及"**工作区**"或"**工作台**"。

```
你：用工作台帮我实现一个用户登录功能
```

或者：

```
你：创建一个工作区，帮我做用户登录功能
```

AI 会自动创建工作区并开始工作。下面是一个完整的对话示例：

---

**对话示例：实现登录功能**

```
你：用工作台帮我实现一个用户登录功能

AI：好的，我来创建工作区管理这个任务。

    📋 工作区已创建：用户登录功能
    🌐 WebUI 地址：http://localhost:19540/workspace/ws-xxx

    让我先了解一下你的项目情况...

    [AI 开始探索代码库]

    我看到你的项目是一个 Express + React 应用，已有用户模型。

    我制定了以下计划：
    1. 设计登录 API 接口
    2. 实现后端认证逻辑（JWT）
    3. 创建前端登录表单
    4. 添加登录状态管理

    确认开始执行吗？

你：好

AI：开始执行第一个任务：设计登录 API 接口

    [AI 开始工作...]

    ✅ 任务 1 完成：
    - 设计了 POST /api/auth/login 接口
    - 入参：email, password
    - 出参：token, user info

    继续执行任务 2：实现后端认证逻辑

    [继续工作...]

你：（可以随时在浏览器打开 WebUI 查看进度）

AI：🎉 所有任务已完成！

    总结：
    - 新增文件：src/routes/auth.js, src/components/Login.tsx
    - 修改文件：src/App.tsx, src/store/index.ts
    - 测试方式：访问 /login 页面

    还有其他需要吗？
```

---

**关键点**：

1. **你不需要学新命令**——用自然语言说任务就行
2. **AI 会主动创建工作区**——不需要你手动操作
3. **计划需要你确认**——AI 不会擅自开始执行
4. **过程可视化**——随时打开 WebUI 看进度

## 术语表

在深入使用之前，先了解几个核心概念。这些术语会在后文反复出现。

### 基础结构

| 术语 | 含义 |
|------|------|
| **工作台** | TanmiWorkspace 本身，管理所有工作区的平台 |
| **工作区** | 单个任务的完整记录，包含目标、规则和一棵任务树 |
| **节点** | 任务树中的每个任务单元，有类型、状态和内容 |

### 节点类型

每个节点有一个类型，决定它的用途：

| 类型 | 用途 | 典型场景 |
|------|------|----------|
| **planning**（规划） | 拆分和组织子任务 | "实现登录功能"拆成"设计接口"+"实现后端"+"实现前端" |
| **execution**（执行） | 实际执行工作 | 写代码、调研、测试 |

**关系**：规划节点像文件夹，执行节点像文件。一个规划节点下可以有多个子节点（规划或执行）。

**补充概念**：

| 术语 | 含义 |
|------|------|
| **MEMO** | 独立于节点树的草稿区，用于存储长内容（设计文档、调研结果等） |
| **引用** | 节点可以引用其他节点、MEMO 或外部文档，形成知识关联 |

MEMO 适合存放跨节点复用的内容，比如一份设计方案可能被多个执行节点引用。

**使用场景**：当内容不适合直接记录在节点中时（长文档、独立方案、跨节点复用的内容），可以让 AI 创建 MEMO：

```
你：这个设计方案太长了，单独记录一下
AI：好的，我创建一个 MEMO 来存放设计方案。

    📝 MEMO 已创建：登录模块设计方案
    已关联到当前节点。
```

MEMO 由 AI 创建，可被多个节点引用。

### 节点状态

节点的生命周期通过状态流转表示：

**执行节点状态**：

| 状态 | 含义 | 下一步 |
|------|------|--------|
| **pending** | 等待开始 | AI 会按顺序执行，进入 implementing |
| **implementing** | 正在执行 | AI 完成后进入 completed，失败进入 failed |
| **completed** | 已完成 | 终态，任务结束 |
| **failed** | 执行失败 | 可以重试（reopen），重新进入 pending |

**规划节点状态**：

| 状态 | 含义 | 下一步 |
|------|------|--------|
| **pending** | 等待开始 | 开始规划，进入 planning |
| **planning** | 正在规划 | 子节点创建完成后，进入 monitoring |
| **monitoring** | 等待子任务完成 | 所有子节点完成后，进入 completed |
| **completed** | 所有子任务完成 | 终态 |
| **cancelled** | 已取消 | 终态，任务放弃 |

### 特殊节点角色

某些执行节点有特殊角色，用于特定用途：

| 角色 | 用途 | 何时出现 |
|------|------|----------|
| **info_collection**（信息收集） | AI 主动探索项目——扫描代码、读文档、理解架构 | 你没提供完整信息，AI 需要自己了解 |
| **info_summary**（信息总结） | AI 整理已有信息——从对话/你提供的设计方案中提取 | 你已提供完整设计方案或需求描述 |
| **dispatch_exec** | 派发任务的执行部分 | 启用派发模式时 |
| **dispatch_spec** | 派发任务的规格审查 | 启用派发模式时 |
| **dispatch_quality** | 派发任务的质量审查（可选） | 启用派发模式且开启质量审查时 |

**info_collection vs info_summary**：二选一。AI 会根据你提供的信息完整度决定用哪个：
- 你说"帮我实现搜索功能"→ AI 需要 info_collection，先探索代码库
- 你说"根据这个设计文档实现搜索功能"（附设计方案）→ AI 用 info_summary，整理你提供的信息

### 节点记录的信息

每个节点会记录以下内容，帮助追踪任务全貌：

| 字段 | 用途 | 何时记录 | 对话中如何触发 |
|------|------|----------|----------------|
| **requirement**（需求） | 任务描述、目标 | 创建节点时 | AI 自动记录，或你说"任务是..." |
| **acceptanceCriteria**（验收标准） | WHEN/THEN 格式的验收条件 | 意图对齐时 | AI 整理后记录 |
| **notes**（笔记） | 过程中的发现、决策 | 执行过程中 | 你说"记一下..."或 AI 主动记录 |
| **conclusion**（结论） | 完成时的总结 | 任务完成时 | AI 完成时必须填写 |
| **docs**（引用） | 关联的文档、MEMO、其他节点 | 任意时刻 | 你说"引用这个文档..." |
| **Log**（日志） | 操作记录（谁在何时做了什么） | 自动记录 | 关键操作自动记录 |
| **Problem**（问题） | 当前阻碍和下一步计划 | 遇到问题时 | 你说"卡住了"或 AI 主动记录 |

**查看方式**：
- **WebUI**：点击节点查看详情，包括需求、结论、日志、问题
- **对话中**：问 AI "这个节点的结论是什么"、"现在卡在哪里"

### 派发模式

处理复杂任务时的一种执行方式：

| 模式 | 特点 | 适用场景 |
|------|------|----------|
| **普通模式** | AI 直接执行，所有步骤在当前会话 | 简单任务、逻辑强依赖完整上下文的任务 |
| **派发模式** | 子任务派发给独立 Agent 执行，完成后审查 | 复杂任务、可独立执行的子任务 |

**派发节点状态**（仅在派发模式下）：

| 状态 | 含义 |
|------|------|
| **pending** | 等待执行 |
| **executing** | 子 Agent 正在执行 |
| **passed** | 审查通过 |
| **failed** | 审查失败，需重试 |

### 能力包

信息收集或信息总结阶段可选的功能模块，根据任务场景自动推荐：

| 能力 | 用途 |
|------|------|
| **intent_alignment** | 意图对齐——澄清需求，确认验收标准 |
| **context_discovery** | 上下文探索——扫描项目，理解架构 |
| **solution_design** | 方案设计——设计接口和实现路径 |
| **verification_strategy** | 验证策划——设计测试用例 |
| **diagnosis** | 问题诊断——定位 bug 根因 |
| **tech_research** | 技术调研——评估技术选型 |
| **measurement_analysis** | 度量分析——性能基准测试 |

### 其他概念

| 术语 | 含义 |
|------|------|
| **会话绑定** | AI 会话与工作区的关联，确保对话中的操作作用到正确的工作区 |
| **聚焦节点** | 当前正在操作的节点，AI 的工作上下文 |
| **WebUI** | 浏览器中的可视化界面，实时展示任务树和执行日志 |

## 完整使用流程

一个任务从开始到结束会经过 5 个阶段。了解这些阶段能帮你更好地与 AI 协作。

### 阶段一：启动任务

**触发方式**：在对话中明确提及"**工作区**"或"**工作台**"

| 示例 | 说明 |
|------|------|
| "用工作台帮我实现搜索功能" | 提及"工作台" |
| "创建一个工作区做这个任务" | 提及"工作区" |
| "帮我实现搜索功能" | ❌ 不会触发，需加上"工作台/工作区" |

**AI 会做什么**：

1. 创建工作区（自动）
2. 告知 WebUI 地址（你可以在浏览器打开查看）
3. 询问任务场景（新功能/修复/优化/总结）

**你会看到**：

```
AI：好的，我来创建工作区管理这个任务。

    📋 工作区：搜索功能开发
    🌐 WebUI：http://localhost:19540/workspace/ws-xxx

    这个任务属于哪种场景？
    1. 新功能开发
    2. Bug 修复
    3. 性能优化
    4. 总结分析

你：1（或直接说"新功能"）
```

### 阶段二：信息收集/整理

根据你提供信息的完整度，AI 会选择不同的方式：

**方式一：信息收集（info_collection）**

当你只说了"帮我做XXX"，AI 需要**主动调研**：

```
AI：让我先了解一下项目情况...

    [扫描项目结构、读取文档]

    我看到：
    - 技术栈：Express + React
    - 有两套 API：v1（旧）和 v2（新）

    新功能应该加在哪个版本？

你：v2

AI：明白了，继续分析...
```

**方式二：信息总结（info_summary）**

当你已经详细描述了需求，或提供了完整设计方案，AI 只需要**整理确认**：

```
你：用工作台帮我做用户登录，要求：
    - 用 JWT 认证
    - 支持邮箱和手机号登录
    - 登录失败 3 次锁定 15 分钟

AI：我来整理一下你的需求：

    ## 需求确认

    | WHEN | THEN |
    |------|------|
    | 用户输入正确凭据 | 返回 JWT token |
    | 登录失败 3 次 | 账号锁定 15 分钟 |
    | 锁定期间尝试登录 | 显示剩余锁定时间 |

    还有其他要求吗？

你：没了

AI：好的，开始规划任务...
```

**AI 如何选择**：
- 你没提供项目细节 → 信息收集（探索代码库）
- 你已经描述得很清楚 → 信息总结（整理确认）

### 阶段三：确认计划

**这是最重要的检查点**——AI 会在这里暂停，等你确认。

**你会看到**：

```
AI：信息收集完成，我制定了以下计划：

    1. [规划] 设计搜索接口
       - 定义 API 路由和参数
       - 确定返回数据结构

    2. [执行] 实现后端搜索逻辑
       - 验收：GET /api/v2/search?q=xxx 返回结果

    3. [执行] 创建前端搜索组件
       - 验收：搜索框输入后显示结果列表

    4. [执行] 添加搜索防抖和加载状态
       - 验收：输入停顿 300ms 后才触发搜索

    确认开始执行吗？
```

**你可以**：

| 你说 | AI 会 |
|------|-------|
| "好" / "可以" / "继续" | 开始执行计划 |
| "第 3 个先不做" | 调整计划，跳过该任务 |
| "把 2 和 3 合并" | 重新规划 |
| "加一个分页功能" | 在计划中追加任务 |
| "等等，先看看现有的搜索代码" | 暂停，AI 会去查看 |

### 阶段四：执行任务

**AI 会按顺序执行计划**，每个任务都会：

1. **开始前**：标记任务为"进行中"
2. **执行时**：写代码、记录日志
3. **完成后**：写结论、标记为"已完成"

**你可以**：

```
你：做到哪了？

AI：当前进度：
    ✅ 任务 1：设计搜索接口（已完成）
    🔄 任务 2：实现后端搜索逻辑（进行中）
    ○ 任务 3：创建前端搜索组件（待开始）
    ○ 任务 4：添加搜索防抖（待开始）

    正在实现后端搜索逻辑，预计还需 2-3 分钟。
```

**WebUI 状态说明**：

| 图标/颜色 | 状态 | 含义 |
|-----------|------|------|
| ○ 灰色 | pending | 等待执行 |
| ◐ 蓝色 | implementing | 正在执行 |
| ● 绿色 | completed | 已完成 |
| ✕ 红色 | failed | 执行失败 |
| ⊘ 黄色 | monitoring | 等待子任务 |

### 阶段五：完成交付

**所有任务完成后，AI 会汇报**：

```
AI：🎉 搜索功能开发完成！

    完成情况：
    ✅ 设计搜索接口 - 定义了 SearchRequest/SearchResponse 类型
    ✅ 实现后端逻辑 - 支持关键词搜索和分页
    ✅ 创建前端组件 - SearchBox + SearchResults
    ✅ 添加防抖优化 - 300ms 防抖 + 加载状态

    新增文件：
    - src/api/v2/search.ts
    - src/components/Search/index.tsx
    - src/hooks/useSearch.ts

    修改文件：
    - src/routes/index.ts（添加路由）
    - src/App.tsx（添加搜索入口）

    测试方式：
    1. 启动开发服务器：npm run dev
    2. 访问首页，点击右上角搜索图标
    3. 输入关键词，应该能看到搜索结果

    还有其他需要吗？
```

**你可以**：

- 确认完成，结束任务
- 提出新需求："再加一个搜索历史功能"
- 报告问题："搜索结果没有高亮关键词"

## 如何保证 AI 行为

你可能会问：AI 真的会按流程做事吗？会不会跳步骤、忘记记录、自己验证自己？

TanmiWorkspace 用四层机制确保 AI "不得不"按规矩来：

### 状态机：物理级约束

普通 AI 助手全靠"自觉"——你说"先规划再执行"，AI 可能直接开始写代码。

TanmiWorkspace 不信任自觉，用**状态转换表**强制约束：

| 可能的问题 | 常见Spec | TanmiWorkspace |
|-------------|---------|----------------|
| AI 跳过规划直接执行 | 可能发生 | 不可能：节点必须从 pending→implementing，跳不过 |
| 任务没完成就说"完成了" | 靠自觉 | 不可能：complete 需要填写 conclusion，系统验证 |
| 同时做多个任务导致混乱 | 可能发生 | 不可能：同级节点只能有一个在执行中 |
| 子任务没做完就汇总 | 可能发生 | 不可能：父节点 complete 前会检查所有子节点状态 |

**实际效果**：AI 尝试非法操作时，系统直接拒绝并返回错误提示，而不是"希望"AI 遵守。

### 自动监视与引导

每次 AI 调用工具（修改代码、执行命令、操作节点），系统都会自动：

1. **记录**：在日志中追加"谁在何时做了什么"
2. **引导**：返回下一步必须做什么

| 可能的问题 | 常见Spec | TanmiWorkspace |
|-------------|---------|----------------|
| AI 改了代码但没记录 | 经常发生 | 不可能：Hook 自动拦截每个修改操作并记录 |
| AI 不知道下一步做什么 | "完成了，接下来呢？" | 系统自动返回 actionRequired，精确指导 |
| AI 在多个任务间跳来跳去 | 聚焦点漂移 | Hook 自动聚焦到最后操作的节点 |

### Skill：标准化流程

市面上的 AI 助手用提示词引导行为，但提示词是建议，AI 可以忽略。

TanmiWorkspace 的 Skill 是**强制性 SOP**：

- **信息收集**：必须按"定位入口→分析依赖→追踪数据流→输出快照"的流程
- **意图对齐**：必须产出 WHEN/THEN 格式的验收标准
- **任务执行**：必须按"评估→计划→执行→验证→交付"五步走
- **规格审查**：必须逐条验证验收标准，任何一条失败=整体失败

| 可能的问题 | 常见Spec | TanmiWorkspace |
|-------------|---------|----------------|
| 每次执行方式不一致 | 看心情 | 同类任务强制走相同流程 |
| 说"完成了"但没验证 | 靠自觉 | Skill 强制：执行→验证→记录→完成，缺一不可 |
| 验证走过场 | 自己检查自己 | 审查 Skill 要求逐条验证，附带证据 |

### 派发系统：执行与审查分离

这是 TanmiWorkspace 核心设计之一：**让不同的 AI 相互检查**。

常见Spec是"自己做自己查"——就像考试自己批卷子，很难客观。

派发模式下，系统会启动多个独立 AI：

| 角色 | 职责 | 约束 |
|------|------|------|
| **执行者**（tanmi-executor） | 写代码、实现功能 | 只能改需求范围内的代码，完成后提交审查 |
| **规格审查**（tanmi-reviewer） | 验证是否符合需求 | **不能修改代码**，必须独立验证，不信任执行者的结论 |
| **质量审查**（tanmi-reviewer） | 检查代码质量 | **不能修改代码**，检查可读性、安全性、性能 |

| 可能的问题 | 常见Spec | TanmiWorkspace 派发模式 |
|-------------|---------|------------------------|
| 自己做自己查 | 总是这样 | 执行与审查由不同 AI 完成 |
| 审查倾向于通过 | 利益冲突 | 审查者无法修改代码，只能判 pass/fail |
| 失败后代码残留 | 手动回滚 | Git 模式自动回滚到执行前 |
| 重试没有方向 | 从头再来 | 失败原因会传递给下一次执行 |

### 为什么这套机制有效？

核心哲学：**不依赖 AI 的"自觉"，用系统强制确保合规**。

```
常见Spec流程的信任链：
  用户 → 相信 AI → AI 自觉遵守 → 结果

TanmiWorkspace 的信任链：
  用户 → 系统强制 → AI 不得不遵守 → 结果
         ↑
    状态机拒绝非法操作
    Hook 自动记录和引导
    Skill 强制标准流程
    派发分离执行与审查
```

**你能感知到的变化**：

- 打开 WebUI，每个节点都有完整的日志，知道 AI 做了什么
- AI 不会跳过中间流程，必须一步步走完流程
- 派发模式下，你能看到执行、审查、质量检查三个独立的记录
- 出问题时，能追溯到具体哪一步出了问题

**上下文自动压缩时的处理**：

- **使用派发模式**：复杂任务用派发模式执行，子 Agent 独立运行，不占用主会话上下文
- **及时记录关键信息**：让 AI 把重要决策和发现记录到节点的 notes 或 conclusion 中

### 派发模式

对于复杂任务，AI 可以把子任务派发给专门的执行器。

**派发模式 vs 普通模式**：

| 对比 | 普通模式 | 派发模式 |
|------|----------|----------|
| 执行者 | 主 AI 直接执行 | 专门的 executor 执行 |
| 上下文 | 完整对话上下文 | 只有当前任务上下文 |
| 审查 | 无 | 自动规格审查 |
| 回滚 | 手动 | 自动（Git 模式） |
| 适合 | 简单任务、强依赖完整上下文的任务 | 复杂任务、可独立执行的子任务 |

**什么时候用派发模式**：

| 任务类型 | 建议 | 原因 |
|----------|------|------|
| 中大规模代码任务 | ✅ 推荐派发 | 可拆分为独立单元执行 |
| 整理/梳理任务 | ✅ 推荐派发 | 用派发整理局部结论，再集中总结 |
| 小规模任务 | ❌ 不推荐 | 派发开销可能超过收益 |
| Bug 修复 | ⚠️ 部分使用 | 上下文强相关，可只用派发做验证环节 |

**简单判断**：如果任务能拆成多个"互不依赖"的子任务，就适合派发。

**对话示例**：

```
你：这个任务比较复杂，用派发模式

AI：好的，启用派发模式。

    派发模式说明：
    - 每个子任务由独立的 executor 执行
    - 执行完成后会有 reviewer 审查结果
    - 失败时自动回滚代码变更

    当前任务会被派发为：
    1. 执行器执行 → 2. 规格审查 → 3. 质量审查（可选）

    确认启用？

你：好

AI：派发模式已启用。

    开始派发任务 1 给 tanmi-executor...

    [executor 独立执行]

    ✅ 执行完成
    开始规格审查...

    [reviewer 检查结果]

    ✅ 规格审查通过
    - 所有验收标准满足
    - 代码变更已合并

    继续派发下一个任务...
```

**质量审查（可选）**：

质量审查用于检查代码可读性、安全性、性能等，适合以下场景：

| 场景 | 建议 |
|------|------|
| 代码质量要求高 | ✅ 开启 |
| 重构/优化任务 | ✅ 开启 |
| 快速迭代/原型开发 | ❌ 可不开启，节省时间 |

AI 默认倾向不开启。你可以通过对话告知 AI：
- "这个任务开启质量审查"
- "最后一个子任务做质量审查"
- "重构相关的任务都要质量审查"

**成本与回滚**：

- **时间消耗**：派发模式为每个子任务构建独立上下文并进行完整的实现——验证流程，时间消耗比普通模式更高。适合用在复杂或中大型任务上。
- **自动回滚**：是 **Git 模式专属**功能，通过 Git 分支管理实现。

> ⚠️ **注意**：Git 模式涉及 Git 操作，属于**实验功能**。使用前建议做好代码备份。

### 工作区管理

**归档与删除**

完成的工作区建议**归档**而非删除：

```
你：把这个工作区归档
AI：已归档工作区：博客评论功能
```

| 处理方式 | 说明 |
|----------|------|
| **归档**（推荐） | 不会被 AI 直接查询到，提高巡检效率；可供后期复盘 |
| **删除** | 不建议删除流程完备的工作区，会丢失执行记录 |

> **提示**：归档的工作区仍保留在 `.tanmi-workspace/` 目录中，需要时可以恢复。

**暂停与恢复**

如果需要暂停任务，不建议直接关闭对话。更好的做法：

```
你：我要离开了，把当前进度记录一下
AI：好的，我来记录当前状态...

    [记录到节点 notes/conclusion]

    已记录：
    - 当前在：任务 3 - 创建评论组件
    - 进度：组件结构已完成，样式待实现
    - 下一步：添加 CSS Module 样式

    下次继续时说"看看工作区状态"即可恢复。
```

**原因**：直接关闭可能导致执行中的节点状态不完整。让 AI 先记录上下文，后续恢复更顺畅。

**导入导出**

工作区支持导出为 `.twsp` 文件，便于备份、迁移或分享：

| 操作 | 入口 | 说明 |
|------|------|------|
| **导出** | 工作区详情页 →「EXPORT」按钮 | 导出为 .twsp 文件，包含完整工作区数据 |
| **导入** | 设置 → 索引管理 → 管理 | 拖拽 .twsp 文件或目录，自动扫描导入 |

导入支持三种方式：
- 拖拽 `.twsp` 文件直接导入
- 拖拽项目目录自动扫描
- 手动输入路径

> **提示**：导入功能还可以扫描已索引路径，发现新工作区并清理无效条目。

### OpenSpec 导入（实验功能）

## 问题诊断

### FAQ：常见问题

**Q1：工作区是什么？我必须用吗？**

工作区是一个任务的完整记录，包括需求、计划、执行过程、结论。你不是必须用——但当任务超过 3 步时，工作区能帮 AI 保持清晰的思路，也让你能追踪进度。

**Q2：我可以不用工作台直接让 AI 做吗？**

可以。只要不提及"工作区"或"工作台"，AI 会直接执行而不创建工作区。比如直接说"帮我改个 bug"，AI 就会像平常一样工作。适合简单的一次性任务。

**Q3：为什么 AI 会问我确认计划？能跳过吗？**

这是防止 AI 跑偏的关键检查点。你可以说"以后不用确认了"，但建议保留——看一眼计划只需要 10 秒，但修复跑偏的结果可能要 10 分钟。

**Q4：任务太大了，AI 做不完怎么办？**

说"这个太大了，帮我拆分"。AI 会把大任务分解成多个小任务，每个都有明确的验收标准。

**Q5：AI 做错了怎么办？**

说"这个不对，重新做"或"回滚"。如果是派发模式，代码会自动回滚；如果不是，你可能需要手动 git reset。

**Q6：怎么看 AI 做了什么？**

- **日常查看**：打开 WebUI，直观展示任务树、节点详情、执行日志
- **查看元数据**：只有需要查看底层管理数据时，才去 `.tanmi-workspace/` 目录

**Q7：关掉对话后工作区还在吗？**

在。工作区存储在项目目录的 `.tanmi-workspace/` 下，不会因为关闭对话而丢失。下次说"继续"就能恢复。

**Q8：一个项目可以有多个工作区吗？**

可以。每个工作区是独立的任务，你可以同时进行多个任务。但建议完成一个再开始下一个，避免上下文混乱。

**Q9：派发模式和普通模式有什么区别？**

详见 [进阶功能 > 派发模式](#派发模式适合复杂任务)。简单来说：普通模式由主 AI 直接执行，派发模式将子任务交给专门的 executor，适合可拆分的中大型任务。

**Q10：为什么有时候 AI 不创建工作区？**

因为你没有明确提及"工作区"或"工作台"。试试说"用工作台帮我做xxx"或"创建一个工作区"。

**Q11：我可以手动操作节点吗？**

| 操作类型 | 能否操作 | 说明 |
|----------|---------|------|
| 节点逻辑关系（添加/删除/状态转换） | WebUI 可操作 | 仅在 AI 出现重要纰漏时使用，AI 会在下次调用时收到通知 |
| 节点内容（需求/结论/笔记） | 需修改原始数据 | AI 总结不准确时可人工修正，但不会通知 AI |

**原则**：优先让 AI 自行修复问题。手动操作是最后手段。

**Q12：我手动改了代码，会影响工作区吗？**

不会。工作区只记录任务结构和执行日志，不跟踪代码文件变化。你可以随时手动修改代码，工作区不会受到影响。但建议在 AI 执行任务期间避免同时修改相关代码，以免产生冲突。

**Q13：WebUI 打不开怎么办？**

1. **检查服务状态**：`tanmi-workspace webui status`
2. **重启服务**：`tanmi-workspace webui restart`，然后刷新页面
3. **端口被占用**：`HTTP_PORT=19542 tanmi-workspace webui`

**Q14：工作区完成后怎么处理？暂停任务怎么办？**

详见 [进阶功能 > 工作区管理](#工作区管理)。简单来说：完成后建议归档而非删除；暂停前让 AI 记录当前进度。

### 发现问题的信号

| 现象 | 可能原因 | 解决方法 |
|------|----------|----------|
| AI 直接执行不问确认 | 跳过了计划确认步骤 | 说"先展示计划让我确认" |
| 没有告知 WebUI 地址 | AI 遗漏关键步骤 | 说"WebUI 地址是什么" |
| 节点直接变成完成 | AI 跳步操作 | 说"请先 start 节点再执行" |
| AI 长时间没响应 | 执行卡住或出错 | 说"怎么了？有什么问题吗" |
| AI 说"我不确定" | 信息收集不充分 | 说"先收集信息再规划" |
| 结论很模糊 | AI 没有总结 | 说"这个节点的结论是什么" |
| 做了一半说完成了 | 验收标准不清晰 | 说"验收标准是什么？都满足了吗" |

### 纠正 AI 的标准话术

当你发现 AI 行为不对时，可以用这些话术纠正：

| 问题 | 你可以说 |
|------|----------|
| 跳过确认 | "先展示计划让我确认" |
| 没给链接 | "WebUI 地址是什么" |
| 跳步操作 | "请先 start 节点再执行" |
| 没记录 | "把这个记下来" |
| 忘记结论 | "这个节点的结论是什么" |
| 任务太大 | "这个太大了，拆分一下" |
| 做错了 | "这个不对，重新做" |
| 卡住了 | "有什么问题吗？需要我帮忙吗" |
| 想放弃 | "这个先不做了" |

## 已知局限

以下是当前版本的已知局限。我们区分了"可改进"（未来可能通过优化解决）和"架构性"（由设计决定，短期不会改变）两类。

### 可改进的局限

**长对话下 AI 对工作台的唤起能力下降**

当单个对话流程较长时，AI 可能逐渐"忘记"主动使用工作台工具，回到普通对话模式。这是 AI 上下文管理的固有挑战。

- **表现**：AI 开始直接回答而不更新节点，或忘记记录结论
- **应对**：提醒 AI"用工作台记录一下"或"更新节点状态"
- **展望**：随着 AI 能力提升和提示优化，此问题有望改善

**上下文恢复依赖记录完整性**

暂停任务后恢复时，AI 能恢复多少上下文取决于之前记录的完整性。如果节点的 conclusion/notes 记录不充分，恢复后 AI 可能遗漏关键信息。

- **表现**：恢复后 AI 对之前的决策细节不清楚
- **应对**：暂停前让 AI 充分记录当前状态；恢复后先查看节点内容确认
- **展望**：可通过更智能的自动记录机制改善

**需求变更后节点结构可能不够理想**

在项目进行中二次添加需求或修改需求时，新增的节点结构可能与原有规划不协调，或组织方式不够美观。这是由工作台的上下文机制和 AI 当时的上下文状态共同决定的。

- **表现**：新增节点位置不合理，或与原有节点的层级关系混乱
- **应对**：添加需求后，可让 AI "重新整理一下工作区结构"或具体描述期望的组织方式
- **展望**：可通过增强引导机制优化，但由于 AI 决策的动态性，难以彻底解决

### 架构性的局限

**派发模式需要 AI 支持 subagent**

派发模式依赖 AI 助手的 subagent（子代理）能力来执行子任务。并非所有 MCP 兼容的 AI 助手都完整支持此功能。

- **Claude Code**：完全支持
- **Cursor**：subagent 支持有限，派发模式可能无法正常工作
- **其他 MCP 助手**：取决于具体实现

这是 MCP 协议生态的现状，非工作台本身的限制。

**历史工作区需手动管理**

工作区不会自动删除或归档。随着使用时间增长，`.tanmi-workspace/` 目录下会积累历史工作区。

- **设计原因**：自动清理可能误删有价值的历史记录
- **应对**：定期归档已完成的工作区；不再需要的可手动删除
