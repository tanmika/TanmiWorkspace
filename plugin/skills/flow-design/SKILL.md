# 方案规划阶段引导

## Announcement (MANDATORY)

Before executing this skill, you MUST announce to the user:

「我将使用 **方案规划阶段引导** 技能来将设计方案分解为规划节点和执行节点。」

---

## 第一步：确认进入阶段

调用以下命令确认进入规划阶段：

```typescript
signal(workspaceId: "...", code: "VzaWdu")
```

---

## 第二步：阶段约束

当前阶段禁止以下操作：
- ❌ Write/Edit/MultiEdit 文件
- ❌ 派发执行（dispatch_node/dispatch_create）
- ❌ 执行任务（保持 exec 节点在 pending 状态）

允许的操作：
- ✅ 创建 planning 节点
- ✅ 创建 execution 节点（但不执行）
- ✅ 更新节点（node_update）
- ✅ 创建 MEMO 记录详细规划

---

## 第三步：分析设计方案

### 3.1 回顾设计产出

从信息阶段的结论中提取：
- 设计概要/构想
- 影响范围（文件、模块）
- 接口定义
- 实现步骤

### 3.2 根据场景选择规划策略

根据场景类型，遵循对应的规划模板：

#### Feature 场景（TDD 驱动）

**结构要求**：所有 exec 必须在 plan 下，禁止直接挂在根节点。

**强制流程**：

1. **测试定义**（单节点）
   - 详细完成所有接口的目标输入输出设计
   - 验收：测试可运行但失败（红灯状态）

2. **功能实现**（按规模规划）
   - 按需求规模合理规划执行节点及嵌套结构
   - 所有环节需要足量日志
   - 验收：所有测试通过（绿灯状态）

3. **集成验证**（单节点）
   - 所有现有测试通过，无新增警告
   - 通过检查日志和核对计划，确保完成的内容符合规划目标
   - 验收：日志完整 + 计划核对通过

**基本结构**：

```
[plan] Feature: xxx
├── [plan] 测试定义 **有且仅有规模极小时可以直接使用[exec]**
├── [plan] 功能实现（按规模展开）
└── [exec] 集成验证
```

**大规模任务分期**：

当功能规模较大时，分为多期实现，每期独立循环：

```
[plan] Feature: xxx
├── [plan] 第一期
│   ├── [exec] 测试定义（本期范围）
│   ├── [exec/plan] 功能实现
│   └── [exec] 集成验证
└── [plan] 第二期
    ├── [exec] 测试定义（本期范围）
    ├── [exec/plan] 功能实现
    └── [exec] 集成验证
```

#### Debug 场景（诊断驱动）

**结构要求**：所有 exec 必须在 plan 下，禁止直接挂在根节点。

**强制流程**：

1. **问题复现**（单节点）
   - 确认问题可稳定复现，记录复现条件和步骤
   - 复现方式根据问题类型选择：测试用例、手动操作步骤、截图录屏等
   - 验收：问题可稳定复现

2. **根因定位**（单节点）
   - 追踪根因，调试过程记录到 notes
   - 验收：明确根因位置和原因

3. **修复实现**（按复杂度规划）
   - 简单 bug 单节点，复杂问题按模块规划
   - 验收：复现条件下问题不再出现

4. **回归验证**（单节点）
   - 运行所有现有测试，检查无新问题引入
   - 验收：所有测试通过

**基本结构**：

```
[plan] Debug: xxx
├── [exec] 问题复现
├── [exec] 根因定位
├── [exec/plan] 修复实现（按复杂度展开）
└── [exec] 回归验证
```

**大规模/复杂 Bug 分期**：

涉及多模块或系统性问题时分期处理：

```
[plan] Debug: xxx
├── [plan] 第一期：模块A修复
│   ├── [exec] 问题复现
│   ├── [exec] 根因定位
│   ├── [exec] 修复实现
│   └── [exec] 回归验证
└── [plan] 第二期：模块B修复
    └── ...
```

**多次回归说明**：

Bug 修复常需多次迭代。当回归验证发现新问题时：
- 返回 design 阶段重新分析
- 创建新的修复节点
- 做好 design ↔ impl 多次转换的准备

#### Optimize 场景（基准驱动）

**结构要求**：所有 exec 必须在 plan 下，禁止直接挂在根节点。

**强制流程**：

1. **基准测量**（单节点）
   - 建立性能基准，记录当前指标（数值、截图、profile 等）
   - 验收：有明确可对比的基准数据

2. **优化实现**（按优化点规划）
   - 按优化点数量和复杂度规划节点
   - 验收：代码修改完成

3. **效果验证**（单节点）
   - 对比优化前后数据
   - 验收：达到预期优化目标

4. **回归验证**（单节点）
   - 确保功能不受影响
   - 验收：所有测试通过

**基本结构**：

```
[plan] Optimize: xxx
├── [exec] 基准测量
├── [plan] 优化实现（按优化点展开）
├── [exec] 效果验证
└── [exec] 回归验证
```

**多优化点分批**：

优化任务通常有多个优化点，在 design 阶段设计最终分批结构：

```
[plan] Optimize: xxx
├── [exec] 基准测量（全局基准）
├── [plan] 第一批：数据库查询优化
│   ├── [exec/plan] 优化实现
│   ├── [exec] 效果验证
│   └── [exec] 回归验证
├── [plan] 第二批：缓存优化
│   ├── [exec/plan] 优化实现
│   ├── [exec] 效果验证
│   └── [exec] 回归验证
└── [exec] 最终效果验证（对比初始基准）
```

**优化未达标处理**：

当效果验证未达预期时：
- 返回 design 阶段重新分析瓶颈
- 调整或新增优化方案
- 做好 design ↔ impl 多次转换的准备

#### Summary 场景（任务分解驱动）

**结构要求**：所有 exec 必须在 plan 下，禁止直接挂在根节点。

**核心原则**：Summary 场景的重点是**评估规模并进行完全的任务分解**。

**强制流程**：

1. **规模评估与任务分解**
   - 评估总结范围和复杂度
   - 识别所有需要总结的主题/模块/维度
   - 将大任务分解为可独立完成的子任务
   - 验收：任务分解完整，无遗漏主题

2. **产出形式确认**（与用户讨论）
   - 询问用户期望的产出形式：
     - **节点形式**：结论记录在各节点 conclusion 中即可
     - **MEMO 报告**：需要最终产出完整的 MEMO 文档
   - 验收：用户确认产出形式

3. **分主题执行**
   - 按分解的任务逐个执行
   - 每个子任务独立收集、整理、输出
   - 验收：各主题完成

4. **完整性验证**
   - 核对所有主题是否覆盖
   - 如需 MEMO，汇总生成最终报告
   - 验收：覆盖所有要求 + 产出符合约定形式

**基本结构**：

```
[plan] Summary: xxx
├── [exec] 规模评估与任务分解
├── [plan] 主题A
│   ├── [exec] 信息收集
│   └── [exec] 整理归纳
├── [plan] 主题B
│   ├── [exec] 信息收集
│   └── [exec] 整理归纳
├── [plan] 主题C
│   └── ...
└── [exec] 完整性验证（+ MEMO 汇总，如需要）
```

**产出形式模板**：

询问用户时使用：

```
总结任务已分解为 N 个主题，请确认产出形式：
1. 节点形式 - 各主题结论记录在节点 conclusion 中
2. MEMO 报告 - 最终汇总为完整的 MEMO 文档

请选择（1/2）：
```

#### Misc 场景（通用流程）

**结构要求**：所有 exec 必须在 plan 下，禁止直接挂在根节点。

**核心原则**：即使是杂项任务，也必须进行**完整的任务分解和详细规划**。

**强制流程**：

1. **任务分析**
   - 明确任务目标和范围
   - 识别任务的自然分解维度（模块/阶段/角色/批次）
   - 验收：目标清晰，分解维度确定

2. **任务分解**
   - 按识别的维度进行分解
   - 遵循 8/80 规则（每个 exec 8-80 小时工作量）
   - 遵循 100% 规则（子任务之和 = 父任务全部工作）
   - 验收：分解完整，无遗漏

3. **详细规划**
   - 每个节点填写详细需求（≥3 行）
   - 每个节点定义验收标准（≥2 条）
   - 明确节点间依赖关系
   - 验收：节点质量达标

4. **执行顺序确认**
   - 确定执行顺序和并行可能性
   - 验收：顺序合理，依赖清晰

**基本结构**：

```
[plan] Misc: xxx
├── [plan] 模块/阶段A
│   ├── [exec] 子任务A.1
│   └── [exec] 子任务A.2
├── [plan] 模块/阶段B
│   └── ...
└── [exec] 最终验证（如需要）
```

**分解维度参考**：

| 维度 | 适用场景 |
|------|----------|
| 按模块 | 涉及多个独立模块的任务 |
| 按阶段 | 有明显时序依赖的任务 |
| 按角色 | 需要不同技能的任务 |
| 按批次 | 重复性工作或大量数据处理 |

**禁止**：
- ❌ 不分解直接创建单个大 exec
- ❌ 跳过详细规划直接开始执行
- ❌ 需求描述模糊或过于简单

## 第四步：分解任务结构

### 4.1 分层原则

**8/80 规则**：每个执行节点的工作量应在 8-80 小时之间
**100% 规则**：子任务之和 = 父任务的全部工作

### 4.2 何时创建中间 planning 节点

| 判断条件 | 处理方式 |
|----------|----------|
| 任务跨多个模块/子系统 | 按模块创建 plan 节点 |
| 任务有明显的阶段/批次 | 按阶段创建 plan 节点 |
| 任务需要不同技能/角色 | 按角色分组创建 plan 节点 |
| exec 数量超过 5-7 个 | 分组为中间 plan 节点 |

### 4.3 何时直接创建 execution 节点

| 判断条件 | 说明 |
|----------|------|
| 任务单一、边界清晰 | 直接创建 exec |
| 工作量在 8-80 小时内 | 不需要再分解 |
| 再分解不会让项目更易管理 | 停止分解 |

### 4.4 分解完整性验证

问自己：
1. 所有子任务完成后，父任务是否 100% 完成？
2. 是否遗漏了某个步骤？
3. 任务之间的依赖关系是否清晰？

## 第五步：创建节点结构

### 5.1 创建 planning 节点

```typescript
// 1. 创建节点
node_create({
  workspaceId: "...",
  parentId: "...",
  type: "planning",
  title: "[模块/阶段名称]",
  requirement: `[详细需求描述 - 至少 3-5 行]

## 目标
[明确的目标描述]

## 范围
- [涉及的文件/模块]
- [涉及的功能点]

## 约束
- [不能做什么]
- [边界条件]`,
  acceptanceCriteria: [
    { when: "[条件1]", then: "[预期结果1]" },
    { when: "[条件2]", then: "[预期结果2]" }
  ]
})

// 2. 开始规划
node_transition({
  workspaceId: "...",
  nodeId: "[plan-node-id]",
  action: "start"
})
// 状态变为 planning
```

### 5.2 创建 execution 节点

```typescript
node_create({
  workspaceId: "...",
  parentId: "[plan-node-id]",
  type: "execution",
  title: "[动作] [具体目标]",
  requirement: `[详细需求描述 - 至少 3-5 行]

## 目标
[具体要完成什么]

## 影响文件
- [file1.ts]: [要做的修改]
- [file2.ts]: [要做的修改]

## 技术方案
[如有约束，说明具体实现方式]

## 约束
- [不能做什么]
- [需要保持什么不变]`,
  acceptanceCriteria: [
    { when: "[触发条件1]", then: "[预期行为1]", verify: "[cmd] npm test" },
    { when: "[触发条件2]", then: "[预期行为2]", verify: "[manual] 检查..." },
    { when: "[错误条件]", then: "[错误处理]", verify: "[check] 无 TODO" }
  ]
})
// exec 节点创建后保持 pending 状态
```

### 5.3 需求描述质量要求

**禁止**：
- ❌ 1-2 行的需求描述
- ❌ 模糊的描述如"实现功能"、"修复问题"
- ❌ 缺少影响范围的描述
- ❌ 缺少约束说明

**要求**：
- ✅ 至少 3-5 行详细描述
- ✅ 明确的目标和范围
- ✅ 涉及的文件/模块列表
- ✅ 技术约束和边界

### 5.4 验收标准质量要求

**禁止**：
- ❌ 无验收标准
- ❌ 宽泛无意义的描述如"功能正常工作"
- ❌ 无法验证的标准

**要求**：
- ✅ 至少 2 条具体的 WHEN/THEN
- ✅ 包含正常流程和异常流程
- ✅ 每条标准都有明确的验证方法（verify 列）

## 节点完成标准

### Planning 节点完成条件

| 条件 | 说明 |
|------|------|
| 子节点已创建 | 所有必要的子节点都已创建 |
| 需求完整 | 每个子节点 requirement ≥3 行 |
| 验收明确 | 每个子节点 acceptanceCriteria ≥2 条 |
| 100% 覆盖 | 子任务之和 = 父任务全部工作 |
| conclusion 已填写 | 记录规划概述 |

### Execution 节点完成条件（执行阶段使用）

| 条件 | 说明 |
|------|------|
| 验收通过 | 所有 acceptanceCriteria 都通过验证 |
| 无遗留 | 无 TODO/FIXME 标记 |
| 测试通过 | 相关测试全部通过 |
| conclusion 已填写 | 记录实际完成的工作和关键决策 |

**注意**：规划阶段只创建 exec 节点，不执行。exec 节点的完成条件在执行阶段（flow-impl）验证。

## Mandatory Rules

1. MUST call signal first - 确认进入规划阶段
2. MUST review design output - 从信息阶段结论中提取设计
3. MUST wrap exec in plan - 所有 exec 必须在 plan 下，禁止直接挂在根节点
4. MUST follow scenario template - 根据场景类型遵循对应规划模板
5. MUST decompose tasks fully - 完整分解任务，不允许跳过分解直接创建大 exec
6. MUST follow 8/80 and 100% rules - 分解粒度合理
7. MUST write detailed requirements - 每个节点 ≥3 行需求描述
8. MUST define acceptance criteria - 每个节点 ≥2 条验收标准
9. MUST include verify method - 每条标准说明如何验证
10. MUST meet completion criteria - 满足节点完成条件才能转换状态
11. MUST keep exec nodes pending - 不在此阶段执行
12. MUST show plan and ask user - 展示规划并获得用户确认
13. MUST record user answers in notes - 用户的所有回答用 notes 记录（不是 log）
14. MUST use node_reference for citations - 引用 MEMO 或文档必须使用 node_reference，禁止直接引用
15. NEVER modify code - 规划阶段禁止 Write/Edit
16. NEVER dispatch - 规划阶段禁止派发

---

## Red Flags

1. 跳过 signal 直接开始 → 阶段状态未同步
2. 不回顾设计直接分解 → 脱离设计方案
3. exec 直接挂在根节点下 → 必须有 plan 包裹
4. 不做任务分解直接创建大 exec → 必须完整分解
5. 不遵循场景模板 → feature 不用 TDD、debug 不复现先
6. 需求描述只有 1-2 行 → 描述不充分
7. 无验收标准或标准模糊 → 无法验证完成
8. exec 节点超过 8 小时工作量 → 需要继续分解
9. 子任务之和不等于父任务 → 违反 100% 规则
10. 不满足完成条件就转换状态 → 节点质量不达标
11. 在规划阶段修改代码 → 违反阶段约束
12. 不展示规划直接进入执行 → 用户失去确认权
13. 用 log 记录用户回答 → 应使用 notes
14. 直接引用 MEMO 或文档 → 必须使用 node_reference 建立引用关系

- [ ] 已调用 signal 进入规划阶段
- [ ] 已回顾信息阶段的设计产出

### 任务分解
- [ ] 遵循 8/80 规则（每个 exec 8-80 小时）
- [ ] 遵循 100% 规则（子任务之和 = 父任务）
- [ ] 按模块/阶段合理分层
- [ ] 依赖关系清晰

### 节点质量
- [ ] 每个节点需求描述 ≥3 行
- [ ] 每个节点验收标准 ≥2 条
- [ ] 每条验收标准有 verify 方法
- [ ] 无模糊或无意义的描述

### 状态检查
- [ ] 所有 planning 节点为 monitoring
- [ ] 所有 execution 节点为 pending
- [ ] 未执行任何代码修改

### 用户确认
- [ ] 已展示任务树结构
- [ ] 已说明执行顺序建议
- [ ] 已获得用户确认进入执行阶段
